# Your importer still has no KiCad 10 rival

**Short answer: no, KiCad 10 does not have a built-in vendor part importer, and your tool is not made redundant by it.** KiCad 10.0.0 (released 20 March 2026) added importers for whole designs from other CAD programs (Allegro, PADS, gEDA/Lepton), but nothing that takes an Ultra Librarian, SnapEDA or SamacSys zip and installs the symbol, footprint and 3D model into a library ([KiCad 10.0.0 release](https://www.kicad.org/blog/2026/03/Version-10.0.0-Released/)). The nearest native feature is the "remote symbol provider" panel, which pulls parts from a web service you configure; none is set up by default, so it is not a local zip importer. Three third-party tools do overlap with you (Import-LIB-KiCad-Plugin, KiLM's new `kilm import`, and component-importer-for-kicad), but none enforces a `<Type>_<SubCategory>_<Manufacturer>` naming scheme, and none commits to a git submodule. Your preview-before-write step is only partly covered elsewhere, because other tools offer a text dry-run at best. The real danger from KiCad 10 is not competition but file handling: newer file formats, nested library tables, and one tool's documented wipe of `kicad_common.json`, a file your app also writes. The recommendations at the end are mostly about making those writes safe, plus a few cheap ideas borrowed from KiLM.

## KiCad 10 improved library handling but never added a vendor-zip importer

Across the 10.0.1 to 10.0.7 release notes, the import fixes concern Altium, Eagle, PADS, Allegro, CADSTAR, LTspice, EasyEDA Pro and DXF, and none adds a vendor-part feature ([10.0.1](https://www.kicad.org/blog/2026/04/KiCad-10.0.1-Release/), [10.0.5](https://www.kicad.org/blog/2026/07/KiCad-10.0.5-Release/)). The Symbol Editor's File > Import > Symbol only copies symbols out of another KiCad library into the one you have open ([KiCad 10 Schematic Editor manual](https://docs.kicad.org/10.0/en/eeschema/eeschema.html)). Other formats (Altium, Eagle, EasyEDA) can be added as a library, but KiCad will not rename, merge or relink anything, and only KiCad-format footprint libraries can be saved ([PCB Editor manual](https://docs.kicad.org/10.0/en/pcbnew/pcbnew.html)). The vendors' own instructions are still manual: Ultra Librarian tells you to add the symbol file and the `.pretty` folder by hand and load the STEP model yourself ([Ultra Librarian help](https://app.ultralibrarian.com/content/help/kicad-6_0.htm)). SnapMagic says its 3D models are "not integrated" with the footprint ([SnapMagic support](https://support.snapmagic.com/en/articles/5612390-how-to-add-libraries-on-kicad-using-snapeda-desktop-app)).

The one genuinely new thing is the remote symbol provider. A provider publishes a small description file over HTTPS, and KiCad's Remote Symbols panel downloads symbols, footprints and 3D files into a destination folder with a library prefix, adds the library to a table and links the footprint ([metadata source](https://docs.kicad.org/doxygen/remote__provider__metadata_8cpp_source.html), [import helpers](https://docs.kicad.org/doxygen/remote__symbol__import__utils_8h_source.html), [10.0.2 notes](https://www.kicad.org/blog/2026/05/KiCad-10.0.2-Release/)). A secondary source reports the provider list is empty by default and it is an open protocol, not a hosted KiCad service ([ZiroEDA issue #656](https://github.com/ZiroEDA/ziro-designer/issues/656)). I would not expect SnapEDA, Ultra Librarian or SamacSys to become providers soon, since their licences are restrictive, though that is my judgement, not something the sources state. Even if one did, KiCad would name things its own way, not yours. Two caveats: I could not search KiCad's GitLab issue tracker directly, so "no planned importer" rests on absence of evidence. And KiCad 11 (expected around February 2027) shows tabbed symbol and footprint editors and pin-to-pad maps in development, but no vendor import ([Post-V10 news thread](https://forum.kicad.info/t/post-v10-new-features-and-development-news/66611)).

## What only your tool does: naming, one 3D variable, a confirmed preview, and git

Reading the three READMEs and the KiLM pull request side by side, four things appear nowhere. First, nothing validates or builds names like `IC_LDO_TI` or forces the `.kicad_sym` and `.pretty` stems to match. Second, no tool writes one fixed variable such as `${CUSTOM_3DMODEL_DIR}/<file>.step`, though Import-LIB makes its variable configurable and KiLM comes closest. Third, preview-then-install is only a command-line dry-run (KiLM) or a symbol-style preview (component-importer), not a view of the exact name and path changes before any write. Fourth, git is absent: Import-LIB says to use git yourself, and I found no commit logic in any of them, though I read documentation, not source code. The "commit inside the `Custom` submodule first, then update the parent" flow is entirely yours. Note that all three importers handle the same three vendors, so the work you have already scoped is the right work; the unique value is convention enforcement, not extraction.

Your own Ultra Librarian sample shows why those rules matter. The symbol file is named by download timestamp, not part number. The STEP file (`DLV0006A`) sits outside the `KiCADv6/` folder and has a different name from the footprint (`DQK0006B`). The symbol's Footprint field holds the bare name with no `Library:` prefix, and the footprint has no `(model ...)` line at all, so the importer must add one rather than fix one. All eight pins are typed `unspecified` ([your sample, `downloaded_examples/ul_CSD85301Q2.zip`, as read in the notes]). Forum threads report the same missing-prefix problem for SamacSys, and say the symbol shows "invalid footprint" until corrected ([forum thread](https://forum.kicad.info/t/footprint-of-samacsys-component-shown-as-invalid-in-schematic-editor/60895)). The notes also found no real SnapEDA or SamacSys sample yet, so anything said about their internals is documentation and forum hearsay. Vendor-quality warnings apply too: users report significant errors in SnapEDA symbols and footprints, so a preview that surfaces things like "8 pins, all unspecified" is worth more than silent automation ([forum](https://forum.kicad.info/t/snapeda-ultralibrarian-automated-import/36000)).

Should you adopt a rival instead of building? The evidence says no. Import-LIB's one-library-per-vendor layout conflicts with your per-category layout, and adopting KiLM would still leave naming, the 3D variable and git for you to build. KiLM is MIT-licensed, so its design (plan every zip before writing anything, one backup per run, atomic rename, duplicate skip, zip-slip guard) is a good template to copy.

## KiCad 10 risks cluster around file formats, config writes and library tables

**The `kicad_common.json` write is the most serious risk.** Import-LIB issue #100 (KiCad 10.0.4, Windows) reports that its automatic setup shrank `kicad_common.json` from 66 KB to 4 KB, deleting every environment variable, so KiCad dropped each library whose path used `${KICAD_3RD_PARTY}`. The reporter suspects a failed read returned an empty dictionary that was then written back ([issue #100](https://api.github.com/repos/Steffen-W/Import-LIB-KiCad-Plugin/issues/100)). The author's fix in release 2026.10.12 was to stop writing KiCad config files altogether. Your `sync_kicad_path_vars` also reads and writes this file, and your variables (`CUSTOM_3DMODEL_DIR`, `KICAD_LIB_GITHUB`, `WE_3DMODEL_DIR`) live in it. The notes found your machine only has KiCad 9.0 settings (`%APPDATA%\kicad\9.0`), so nothing in the KiCad 10 config has been checked. KiCad 10 uses a separate `10.0` folder per minor version, so the code must find the newest `N.0` folder instead of assuming 9.

**File format versions differ by a lot.** KiCad 10 writes symbol libraries at version 20251024 and footprints at 20260206, in a tab-indented multi-line style, with `(show_name no)` and `(do_not_autoplace no)` inside every symbol property and `(hide yes)` flags ([symbol versions](https://gitlab.com/kicad/code/kicad/-/raw/10.0/eeschema/sch_file_versions.h), [footprint versions](https://gitlab.com/kicad/code/kicad/-/raw/10.0/pcbnew/pcb_io/kicad_sexpr/pcb_io_kicad_sexpr.h)). Your Ultra Librarian sample is the older 20211014 style: single-line properties, `(id N)` tokens and a bare `hide`. KiCad documents formats from 6.0 onward, so older files should load, but the notes found no official statement and no one loaded your sample into KiCad 10. Treat mixed-version libraries as untested. Insert vendor text verbatim and edit only a few tokens (the Footprint value, the `(model ...)` path, the names), scoping each edit to the right symbol so sub-symbols like `NAME_1_1`, `extends` parents and `${REFERENCE}` text are untouched. Import-LIB itself had to fix lost KiCad 9/10 symbol data and a changed pin-hide token in 2026, which shows how easily naive handling breaks. Also, a file saved by KiCad 10 may not reopen in KiCad 9 (a user report), so re-saving through KiCad 10 is a one-way upgrade, and it rewrites every symbol once, producing a large one-time git diff.

**Library tables and path variables changed in smaller ways.** KiCad 10 lets a table contain other tables, and the default global `sym-lib-table` can be a single nested entry, so a regex merge into the global table can miss entries; your generated tables in the repo root remain valid, but "install into the global table" should be tested against a real 10.0 table ([forum](https://forum.kicad.info/t/v10-windows-no-symbol-libraries-found/67890)). Users also report custom libraries going missing or variables imported wrongly on first run of KiCad 10 ([forum](https://forum.kicad.info/t/kicad-10-libraries-path-wrong-imported-from-previous-version-on-first-run/67824)). The built-in 3D variable is now `KICAD10_3DMODEL_DIR`, and older versioned names resolve automatically, but unversioned names do not; your unversioned `CUSTOM_3DMODEL_DIR` is unaffected ([KiCad 10 manual](https://docs.kicad.org/10.0/en/kicad/kicad.html)). Official 3D libraries are STEP-only from 10, which matches your `.step` convention.

**Embedded files and symdir are low-priority edge cases.** KiCad 9 and 10 can embed 3D models inside footprints as compressed base64 blocks. Embedding makes diffs and git history ugly, and the official library convention reportedly forbids it (I could not read that page directly, so treat it as medium confidence), so keep external STEP files, but warn if an incoming file contains `(embedded_files`. The new `.kicad_symdir` layout (one file per symbol) would break your sym/fp pairing and your scanner, and a KiCad developer said the normal multi-symbol `.kicad_sym` remains the standard ([forum](https://forum.kicad.info/t/v10-new-library-handling-kicad-symdir-unpacked/68546)). Finally, case-only footprint renames were buggy until 10.0.7, so avoid relying on KiCad for case changes.

## Recommendations

1. **Harden the `kicad_common.json` write first.** Never write if the read failed or returned empty. Merge only your three variables into the existing data, write to a temporary file and rename, and make a timestamped backup beforehand. Detect the newest `N.0` config folder, and consider making the write opt-in with a preview, as Import-LIB retreated to manual setup.
2. **Do not use kiutils or the KiCad IPC API.** kiutils has had no release since February 2024 and has open bugs with hidden fields; the IPC route needs a running KiCad and, per third-party sources, offers no symbol editing ([kiutils on PyPI](https://pypi.org/pypi/kiutils/json)). Keep your token-level editing with paren-balanced scanning, and make it version-tolerant for both the 2021 style and the KiCad 10 style.
3. **Always rewrite the Footprint field to `<Lib>:<FP>`**, even if a prefix is present, and add a `(model ...)` block when none exists. Pair files by structure (the one `.kicad_mod`, the one STEP), never by filename.
4. **Copy KiLM's safety pattern:** plan all changes for a zip before writing, one backup per run, write-then-rename, skip or ask on duplicates, and validate zip member names against path traversal.
5. **Make the preview earn its keep:** show the new names, the rewritten Footprint value, the 3D path, and warnings (all pins `unspecified`, `embedded_files`, legacy format, name collisions). A forum commenter also raised whether vendor licences allow automated handling, with the answer that manual download avoids the issue, so keep the zip browse manual.
6. **Test on a real KiCad 10 install.** Install KiCad 10.0.7, create a copy of your `Custom` libraries, load a freshly imported UL part in the Symbol Editor and Footprint Editor, and check that your tables load. Add SnapEDA, SamacSys and loose-file samples to `downloaded_examples/` before building those parsers, as your constraints already require.
7. **Do not re-scope.** Skip `.kicad_symdir`, database libraries (they still need correctly named, footprint-linked symbols to point at, which is what you produce) and PCM packaging.

## Conclusion

The competitive picture is more favorable than the file-handling picture. KiCad itself leaves this niche open, and the closest tools differ from yours in exactly the places that matter to you: naming, a single 3D variable, confirmed previews and submodule-aware commits. But the 2026 evidence shows that even a well-regarded importer can damage a user's setup through an unguarded config write, so safe writing, not extraction, is where a personal tool earns trust.

What you are building is better understood as a convention enforcer with a safety harness than as an importer. That framing suggests a cheap path: reuse the proven plan-then-atomic-write approach, keep the vendor text byte-for-byte except for a handful of fields, and spend your testing effort on KiCad 10 rather than on more features. The main open uncertainty is untested ground, since nobody (including these notes) has loaded an old-format vendor file into KiCad 10 or checked a 10.0 `kicad_common.json`, so those two checks are the first things to do.
