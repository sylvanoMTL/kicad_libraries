## Choices made here (planner's discretion)

- **One helper for "bring the heading back".** `HelpDialog._show_current_heading()` scrolls to the current entry's heading: a section to its anchor, a page to its title (scroll value 0). It is called from `show_topic`, whether or not the item changed, and from `showEvent`. `show_topic` covers the show_remembered path and an import window Help on a guide already on Importing Parts. `showEvent` covers every reopen and the fit_window narrowing. It never selects and never saves.
- **When showEvent re-scrolls.** Only for a non-spontaneous show (the app's own show()). A window restored from the taskbar sends a spontaneous show, and a page being read must not jump. The helper runs once at once, after fit_window, and once on the next event-loop turn, to cover layout work Qt posts after the resize. Use the receiver form `QTimer.singleShot(0, self, ...)` so a deleted guide never runs it.
- **A page asked for again goes back to its title.** `show_topic("importing")` on a guide already showing that page scrolls it to the top. This is what "open on Importing Parts" means for the import window's Help.
- **D3 mechanism.** An event filter on the menu viewport tracks a held left button: a left press or left double-click sets `_menu_held`, and the left release clears it. Other buttons never set it; Qt drag-selects only with the left button. While the hold is on, `_on_topic_selected` defers the fold until after the release, then schedules it on the next event-loop turn so the view finishes handling the release first. Keyboard moves and instant clicks behave as today. The filter never consumes an event. Planner's choice over "ignore drag-selection": it keeps Qt's normal drag behaviour and only stops the rows from moving under a still cursor.
- **The hold cannot outlive the button (revision, checker issue 2).** A release can be lost: a popup or modal opens during the press, or the grab is lost. Two guards end the hold, so the flag alone never decides:
  - `_on_topic_selected` defers only when `_menu_held` is set AND `QGuiApplication.mouseButtons()` still reports the left button. Otherwise it drops the stale hold and any waiting fold, and folds on the next turn as today.
  - `hideEvent` ends the hold and runs a waiting fold at once. Qt keeps reporting a button that was down when the window hid, so the live check alone does not cover close.
  - Planner's route, smaller than tracking every release path: the live button state is the truth, and the flag only says the press began on the menu.
  - Grounding (probe 2026-11-10, offscreen, PySide6 6.12, scratchpad only): QTest.mousePress on the window or on the viewport sets `QGuiApplication.mouseButtons()` to LeftButton. A release swallowed by a viewport filter installed later still clears it, and the dialog's filter never sees that release. A hide and show while the button is held keeps LeftButton.
- **Page-row half (revision, checker issue 1).** For the step-1 order (Close, then F1) no mechanism was identified, so none is invented here. Each candidate is pinned or changed (see the residual-risk truth), and the owner's re-check is the stated gate with a blocking trace fallback.
- **Visible guide on an asked topic (revision 2, checker warning).** Route: change plus a RED test, not a residual note.
  - HelpDialog keeps a private flag `_on_asked_topic`. It is set by a successful `show_topic` and cleared at the end of `show_remembered` and by the owner's own saved move in `_on_topic_selected`. A public method `shows_asked_topic() -> bool` returns it.
  - `MainWindow.show_guide` with no topic calls `show_remembered()` when the reused guide is hidden OR `shows_asked_topic()` is True. A visible guide on the owner's own place is only raised, and its page does not move.
  - Why this implements G-12-23 rather than changing it: the owner decided that main-window Help and F1 reopen the page or section the owner last chose. The raise-only rule (12-19, planner's choice) protects the owner's own reading. A place the code put there (an explicit topic, never saved) is not the owner's choice, so main-window Help now goes back to the owner's place there too, as it already does after a Close.
  - Consequence, consistent with the closed-guide path: with nothing saved yet, it goes to the first page (Overview), as a hidden guide does today.
  - A click on the row that is already current emits no `currentItemChanged` and is not saved (12-19). It therefore does not end the asked topic either, so main-window Help still shows the saved place. What main-window Help shows is always what is saved.
