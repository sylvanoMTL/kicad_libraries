## Decisions recorded at plan revision (2026-10-19)

- D-01 on the startup path: a destination table written before Phase 2 can hold both same-nickname peers (the HARD-08 overwrite). Startup pre-selection would then select both, and Generate would refuse with `table.duplicate_nickname`. `_trim_collided_selection` keeps the selected peer whose rel_path sorts first (Custom before WurthElektronik, the same preference as Select All in plan 02-02), unchecks the rest and logs a WARNING. It runs after every scan's selection policy. After Rescan it changes nothing in practice, because the re-applied selection already satisfied D-01 and new libraries start unchecked (D-04).
- CLAUDE.md startup property: the footprints linked to the pre-selected symbols are selected by an additive pass, not by the widget's recompute sync. The recompute would also uncheck footprints the tables selected that no symbol references, which contradicts D-05 startup pre-selection and the startup `Solo` test below. The pass runs at startup only, because HARD-07 and D-04 require Rescan to keep the user's flags as they are.
- Startup is a one-shot flag, not inferred from the scan result (D-04, D-05). `_startup_pending` is set to True in `__init__` before the first `_start_scan` and cleared in `_finish_scan`, which both scan handlers call in `finally`. The first scan therefore consumes it on finish, on error, and when its finish handler raises. Inferring startup from an unset `_scan_result` would treat the Rescan after a failed startup scan as startup and pre-select from the tables. With the flag, that Rescan re-applies the user's selection, which is empty because the tree was never populated. Every library starts unchecked (D-04: libraries seen for the first time start unchecked), no table is read and no linked-footprint pass runs (D-05: only startup pre-selects). So the user is not left guessing, the failed startup scan logs one INFO line saying nothing was pre-selected from the destination tables and that restarting the app pre-selects from them.
