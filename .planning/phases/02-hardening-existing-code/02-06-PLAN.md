<objective>
Stop overlapping scans and stop rescans from resetting the user's selection.

Task 1 turns `_start_scan` into the one guarded funnel for every scan request, disables the scan-sensitive controls while a scan runs, and clears the busy state in `finally` blocks (HARD-05; research reproduced a hard access-violation crash from one Rescan during the startup scan). Task 2 makes table pre-selection startup-only and re-applies the user's selection by `rel_path` on every later scan (D-04, D-05, HARD-07), including collided libraries (HARD-08).

Purpose: the importer's Phase 5 post-import rescan reuses this funnel and this selection policy.
Output: updated `main_window.py` and its offscreen tests.
</objective>

## Open questions resolved here (from 02-RESEARCH.md)

- Busy-guard UX (Claude's discretion): both. Controls are disabled while scanning, and `_start_scan` itself also refuses with an info line, because a disabled control is not a guarantee for programmatic callers (Phase 5 post-import rescan). The guard keys on `self._worker is not None`, not on the thread's running state, because the custom `finished` signal fires while `run()` has not returned yet.
- OQ4 (rescan vs in-progress toggles): no extra work. The progress dialog is window-modal, so the user cannot toggle selection during a scan, and the snapshot is taken from the previous `ScanResult` objects when the new result arrives.
