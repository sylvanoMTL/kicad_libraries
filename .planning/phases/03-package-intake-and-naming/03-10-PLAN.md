## Decisions in this plan (planner, from measurements on this machine)

Measured with the project venv (Python 3.14.4, win32). Peaks are tracemalloc peaks, and "x" is the multiple of the text's size. Scripts are in the session scratchpad and are not repo source.

| `str` handling | 512 KiB plain | 512 KiB escape-dense | 512 KiB mixed | Runs on 3.10 |
|---|---|---|---|---|
| current `"(?:[^"\\]\|\\.)*"` | 116.9 MiB (x234) | 60.1 MiB (x120) | 75.0 MiB (x150) | yes |
| review's unrolled form | 0.0 MiB | 59.8 MiB (x120) | 38.2 MiB (x77) | yes |
| possessive / atomic group | 0.0 MiB | 0.0 MiB | 0.0 MiB | **no**: `re.error` at import |
| **chosen: bounded-window scan** | 0.50 MiB (x1.01, the node's own text) | x1.01 | x1.01 | yes, one code path |

- **Chosen mechanism: a linear scan, `_string_end`, used for every string on every interpreter.** It repeatedly matches `[^"\\]*(?:\\.[^"\\]*){0,1024}`, which is the unrolled body with its escape-pair group bounded to `_STRING_WINDOW = 1024` repeats. The regex engine keeps backtrack state for every repeat of a group that is not a single-character repeat, so bounding the repeat count bounds that state to about 1024 entries (about 250 KB) per call, whatever the string length. The scan then continues from where the window stopped. The results at 8 MiB: plain 0.06 s, escape-dense 0.17 s, mixed 0.13 s, escaped quotes 0.18 s, all at x1.00. On real text it is no slower than the old tokenizer: `_symbol_library(2000)` (2.04 MiB) parses in 0.41 s instead of 0.50 s, and the whole `Custom/` corpus takes 0.063 s against 0.060 s, within noise. Differential check during planning: 0 mismatches against the old `parse` over 22,036 inputs (seeded fuzz, every `Custom/` file, strings straddling window edges).
- **Rejected alternatives.**
  - The review's unrolled pattern alone still keeps a frame per escape. That is about 1 GiB for an escape-dense string at the 8 MiB cap, the same "gigabytes" class.
  - Possessive quantifiers and atomic groups are Python 3.11+ syntax. The floor is 3.10, and raising it is the owner's call.
  - A version-gated possessive pattern would give two code paths, and the 3.10 path could not be run here (`py -0` lists 3.14 and 3.11 only).
  - A per-escape Python loop (a `search` for the next quote or backslash) measured 8.6 s at 8 MiB escape-dense.
- **`parse` moves from `finditer` to an explicit offset loop over `_TOKEN.match`**, because `finditer` cannot jump past a string that was scanned outside the regex. Every position still matches some group (`bad` is kept for that), so the loop sees the same token sequence.
- **`unquote` is part of this gap, because the audit found it.** Old cost at 8 MiB: escape-dense 221 MiB traced (x27.6) and 2.1 s untraced; mixed 178 MiB (x22.2) and 1.4 s. `find_property` unquotes every property name on each call, and `part_meta` makes up to 16 calls. A hostile 256 KiB property name therefore already costs 0.9 s, and at 8 MiB about 28 s plus the tokenizer's gigabytes. The new chain:
  - escaped backslash pairs are replaced by a lone-surrogate placeholder (`"\ud800"`, which strict UTF-8 decoding never produces);
  - then each of `\"`, `\n`, `\r`, `\t` is replaced by its character;
  - then the placeholder becomes one backslash.

  It is exact because `str.replace` pairs each backslash run from its left end, exactly as the regex does. Measured: x1.0 to x4.0 (x4 only for backslash-pair-dense text, from a 2-byte-per-character intermediate), 0.003 to 0.29 s at 8 MiB, and 0 mismatches against the old function over 400,000 tokens. A body that already holds the placeholder takes the old regex path, so the result is exact for any `str`.
- **End to end with both fixes (8 MiB, tracemalloc, `open_package` + `detect_candidate`):**

  | Case | Peak | Time |

That leaves headroom of at least 1.3x over every measured case, and each bound is far below the old code (x120 or more for parse, x22 or more for escape-dense `unquote`).
