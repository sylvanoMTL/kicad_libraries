<objective>
Close verification gap CR-01's second manifestation: `_model_final_names` guards a 3D-model rename candidate against the pre-migration inventory with case-sensitive Python string membership (`footprints.py:329`), while the write op that decision drives is placed via `new_path.exists()` (`footprints.py:485`) — a real, case-insensitive filesystem call on Windows, this project's primary platform. A candidate differing only by letter case from an untouched, unlinked, pre-existing model file therefore passes the guard; its write op's `base_sha256` is seeded from that unrelated file's current bytes, so `_preflight`'s staleness net also passes, and `apply_migration` reports `ok=True` while the unrelated model's content is destroyed. Independently reproduced by both `13-REVIEW.md` CR-01 and the verification session itself.

This plan casefolds the guard (mirroring `claimed_model_names` at `footprints.py:474-475`, which is already built correctly for the D-15 added-model path), adds the regression test `13-REVIEW.md` IN-01 and the gap's second `missing:` item both call for, and makes the whole defect class structurally impossible at the transaction boundary.

Purpose: the phase goal's truth 2 ("one transaction with rollback ... every Footprint field and model path rewritten") is still false for this trigger shape. There is no failure to roll back from, because no failure is detected — the loss is baked into a successful commit. This is the last blocking gap of Phase 13, and the owner's live migration (the `human_verification` item) must not run before it is closed.
Output: the casefolded guard in `footprints.py`, the `migration.rename_would_overwrite` invariant in `applier.py`, and six regression tests across three test files.

Chosen route (the gap left this open; stated here rather than decided silently):

1. **Issue raised: `Severity.INFO` `migration.model_kept_name`, non-blocking** — not a blocking `migration.model_clash`. `13-REVIEW.md` proposes this and the verification's `missing:` item allows either. Three reasons: (a) the exact-match half of this very guard (`footprints.py:329`) already keeps the name with this INFO, and the only difference between the exact and the case-only case is letter case on a filesystem that does not distinguish them — treating them differently would be arbitrary; (b) D-09 settles a case-only clash by keeping the on-disk spelling (Phase 12 D-14), which is exactly "do not rename"; (c) nothing is written or deleted, the part's footprint keeps pointing at its existing model file, and the atomic rule requires only that the model file exist — so Run stays enabled and the whole migration is not blocked by an unrelated leftover file's spelling, which the owner has no in-app way to rename.
2. **Casefold inline; do not call `naming.case_clash`** (`naming.py:113`). It filters out `other == name`, so it cannot replace the exact-match half of this one guard — using it would mean two code paths and two issue codes for one decision; its WARNING `naming.case_clash` text is importer-naming vocabulary, not the migration's own; and it builds a list per candidate where one prebuilt casefolded set is O(1) per lookup.

Task 3 is declared co-located scope: CR-01 has now recurred twice through two different planner paths, and the existing `migration.duplicate_write` backstop is structurally blind to this one (the plan holds a single write op; the destroyed file is referenced by no op at all), so the transaction gets the invariant that catches the class rather than the instance.
